# Deploy with Helm

The `helm/main` chart deploys K8ston via the `helm/k8ston` subchart, with
templated RBAC scope, restart wiring, access config, and NetworkPolicy.
Only the `helm/k8ston` chart is published to OCI; direct-chart values are not
wrapped in `k8ston:` and the direct chart does not include the umbrella's NetworkPolicy.

## Minimal values

```mdx-code-block
import HelmValues from '!!raw-loader!../../.samples/values-helm.yaml';

<CodeBlock language="yaml">{HelmValues}</CodeBlock>
```

The example uses namespace `k8ston`; replace the image version, URLs, client ID,
and group names. Configure a TLS exposure and register the exact provider callback
`https://<your-host>/api/auth/callback`. Absent or empty namespace policy is open,
not deny-all; leaving both admin lists empty makes all authenticated users admins.

`APP_URL` is read at server runtime. Do not bake in a conflicting `NEXT_PUBLIC_APP_URL`,
which takes precedence and can be fixed at build time. Replicas must share a random
signing key and consistent annotation/retention settings.

Create the referenced Secret out-of-band. For a manual initial setup, prepare a
private env file outside the checkout (permissions `0600`) containing your provider's
`OIDC_CLIENT_SECRET` and a fresh `SESSION_SECRET` from `openssl rand -hex 32`.
Do not commit the file or put the actual credential in shell history:

```bash
kubectl apply -f app/k8s/namespace.yaml
kubectl -n k8ston create secret generic k8ston-oidc \
  --from-env-file=/secure/path/k8ston-oidc.env
```

## Key knobs

| Value                                                            | Purpose                                                                                                        |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `k8ston.env`                                                     | Non-secret K8ston config (full reference: `app/.env.example`)                                                  |
| `k8ston.envSecretName`                                           | K8s Secret with `OIDC_CLIENT_SECRET` + `SESSION_SECRET`                                                        |
| `k8ston.rbac.scope`                                              | `namespace` (default) or `cluster` — the chart derives `K8STON_SCOPE` from it (explicit entries must match)    |
| `k8ston.rbac.extraNamespaces`                                    | Curated extra namespaces (namespace scope): Roles plus a derived `K8STON_NAMESPACES` allowlist, no ClusterRole |
| `k8ston.restartEnabled`                                          | Single effective value wiring `K8STON_RESTART_ENABLED` **and** the `apps` RBAC rule together                   |
| `k8ston.accessConfig.enabled`                                    | Renders the access ConfigMap **and** derives `K8STON_ACCESS_CONFIGMAP` from its name (`access.json` key)       |
| `k8ston.replicaCount`                                            | Application replicas; share the signing key and consistent configuration (umbrella default 2).                 |
| `k8ston.ingress.enabled` / `route.enabled` / `httpRoute.enabled` | Expose via Ingress / OpenShift Route / Gateway API HTTPRoute                                                   |
| `networkPolicy.enabled`                                          | Locks down pod traffic (DNS + K8s API egress allowed)                                                          |
| `networkPolicy.allowOpenShiftIngress`                            | **Must be `true` on OpenShift** (routes arrive from `openshift-ingress`)                                       |

See `helm/main/values-example.yaml` and `helm/main/values-k8s-prod.example.yaml`
for fuller examples, including topology spread and IdP egress CIDRs.

## RBAC scope

One effective configuration (`k8ston.effectiveConfig` in the subchart) derives
the chart-managed runtime env from the RBAC/feature values, so the rendered
Deployment env, Role/ClusterRole scope, subjects, and `apps` permissions always
agree. Local `k8ston.env` wins over `global.env` per key. Omit the managed keys
(`K8STON_SCOPE`, `K8STON_NAMESPACES`, `K8STON_RESTART_ENABLED`,
`K8STON_ACCESS_CONFIGMAP`) to use the derived defaults; an explicit entry must
equal the derived effective value, otherwise rendering fails with actionable
guidance instead of deploying disagreeing runtime/RBAC behavior.

- `namespace`: own namespace only (least privilege, the default). The chart
  derives `K8STON_SCOPE=namespace` and renders a Role + RoleBinding.
- `namespace` + `k8ston.rbac.extraNamespaces: [team-a]`: curated
  multi-namespace access. The chart renders a Role + RoleBinding pair per entry
  (subject stays this release's ServiceAccount) and derives
  `K8STON_SCOPE=cluster` with the bounded allowlist
  `K8STON_NAMESPACES=<release-namespace>,team-a` — served by these namespaced
  Roles only, no ClusterRole is rendered. Previously the extra Roles were
  unusable because the namespace runtime scope only exposed the pod namespace.
- `cluster`: centralized dashboard (`K8STON_SCOPE=cluster`); narrow with
  `K8STON_NAMESPACES="team-a,team-b"` in `k8ston.env`. `extraNamespaces` is
  rejected with cluster scope. This allowlist limits the app, not the ClusterRole's
  Kubernetes permissions; curated namespaces can use namespaced Roles instead.
- `rbac.create: false`: RBAC is managed out-of-band. Set `K8STON_SCOPE` /
  `K8STON_NAMESPACES` in `k8ston.env` yourself to match your external grants
  (`rbac.scope`/`extraNamespaces` are then ignored), and grant the `apps`
  permissions yourself to match `k8ston.restartEnabled`.

## Restart + access config in one place

Unlike the raw manifests (where the flag and the RBAC rule are separate manual
steps), the chart wires them together: `k8ston.restartEnabled` is the single
effective value driving **both** the `K8STON_RESTART_ENABLED` runtime flag
**and** the `apps` RBAC rule (an explicit env entry must parse to the same
value — runtime truthy strings are `1/true/yes/on` — or rendering fails).
Similarly, `k8ston.accessConfig.enabled` renders the namespace fallback
ConfigMap instead of applying `app/k8s/configmap-access.yaml` by hand, **and**
derives `K8STON_ACCESS_CONFIGMAP` from `accessConfig.name` so the runtime
policy reader finds it. The key must stay `access.json` (hardcoded by the
reader); with `accessConfig.enabled: false`, point `K8STON_ACCESS_CONFIGMAP`
at an externally managed ConfigMap. Each namespace entry accepts `groups`,
`users`, and an optional `teams` array (see
[Authorization](/guides/authorization/#teams)); deploy the app before adding
`teams`, since older releases reject the unknown field. `extraEnv` entries must
not set managed keys (they render last and would shadow the derived values).

## NetworkPolicy notes

- Pod DNS (UDP/TCP 53) is allowed for both upstream Kubernetes (`kube-system`)
  and OpenShift (`openshift-dns`).
- Egress to the Kubernetes API (`https://kubernetes.default.svc`, a ClusterIP)
  is allowed on ports 443/6443 via `allowKubeApiEgress`.
- Standard NetworkPolicy cannot match DNS names: add your IdP's CIDR ranges
  under `networkPolicy.k8ston.idpEgressIpBlocks` when you tighten API egress.
  The default API-port allowance permits all destinations on those ports; adding
  IdP CIDRs does not narrow that rule. Restrict API and IdP destinations deliberately.
- With this NetworkPolicy enabled, OpenShift Routes require `allowOpenShiftIngress=true`;
  other ingress controllers need appropriate `ingressFrom` allowances.

## Installing with the chart Makefile

`helm/main/Makefile` wraps the standard flow and reads
`values-<namespace>.secret.yaml`. Despite that filename, keep provider/signing
credentials in the referenced Kubernetes Secret, not embedded in the values file.
From the repository root, copy the documentation example without overwriting an
existing file, then customize it for your namespace and platform:

```bash
cp -n website/.samples/values-helm.yaml helm/main/values-k8ston.secret.yaml
RELEASE_VERSION='<published-X.Y.Z-version>'
make -C helm/main lint NAMESPACE=k8ston IMAGE_TAG="$RELEASE_VERSION"
make -C helm/main upgrade NAMESPACE=k8ston IMAGE_TAG="$RELEASE_VERSION"
make -C helm/main template NAMESPACE=k8ston IMAGE_TAG="$RELEASE_VERSION"
```

`template` writes `helm/main/template.yaml`; avoid overwriting useful generated work.
The packaged subchart under `helm/main/charts/` is refreshed by the
`helm-dep` step (`helm dependency update`) before every install, upgrade, lint,
and template run.

## OCI chart releases

Every `v*.*.*` tag publishes the `helm/k8ston` chart to
`oci://ghcr.io/egose/charts/k8ston` (see the _Publish Helm chart_ workflow).
Chart `version` and `appVersion` are set from the release tag, but `image.tag`
still defaults to `latest`. **Pin both chart and image**; `--version` alone does
not pin the app. Choose a published stable `X.Y.Z` release without a leading `v`.

For a direct install, save the app settings at the top level in
`k8ston-direct-values.yaml` (no `k8ston:` wrapper). See the
[chart README](https://github.com/egose/k8ston/blob/main/helm/k8ston/README.md#install-directly)
for a complete direct-chart example. After provisioning the namespace and Secret:

```bash
RELEASE_VERSION='<published-X.Y.Z-version>'
helm upgrade --install k8ston oci://ghcr.io/egose/charts/k8ston \
  --version "$RELEASE_VERSION" \
  --namespace k8ston --create-namespace \
  --values k8ston-direct-values.yaml \
  --set-string image.tag="$RELEASE_VERSION" \
  --wait
```

Or consume it as a dependency (`helm registry login ghcr.io` first if the
package is private):

```yaml
# Chart.yaml
dependencies:
  - name: k8ston
    version: '<published-X.Y.Z-version>'
    repository: oci://ghcr.io/egose/charts
    condition: k8ston.enabled
```

```yaml
# values.yaml
k8ston:
  enabled: true
  image:
    tag: '<published-X.Y.Z-version>'
  envSecretName: k8ston-oidc
  rbac:
    scope: namespace
```

Replace both version placeholders and add authentication, access rules, and
exposure settings under `k8ston:` for dependency usage. See the
[chart README](https://github.com/egose/k8ston/blob/main/helm/k8ston/README.md)
for the full values reference.

## Exposure and health

- One of `ingress`, `route` (OpenShift), or `httpRoute` (Gateway API) exposes
  the ClusterIP Service — enable exactly what your platform provides.
- Liveness and readiness probes hit `/api/config`: unauthenticated and
  K8s/OIDC-free, so it is safe to probe (the raw manifests in `app/k8s/`
  probe the same endpoint). They do not establish working auth or Kubernetes access;
  verify a real sign-in, allowed operations, and an unauthorized-user denial.
- The ServiceAccount token **must** stay auto-mounted
  (`serviceAccount.automount: true`) — K8ston talks to the Kubernetes API
  with its own token.

## Chart CI

The _Helm_ workflow lints both charts and templates them on every `helm/**`
change, including a full-flag matrix for the subchart (cluster scope,
restart, ingress + route + HTTPRoute, access config, autoscaling, PDB,
external ServiceAccount) and both umbrella example values files. It also runs
the rendered-object regressions in `helm/k8ston/tests/render-regressions.sh`
(default, cluster, curated namespaces, local/global conflicts, false
overrides, external RBAC, custom access config, and every contradiction
error). Run the same locally with `helm lint` / `helm template` and the
regression script before opening a PR.
