Authorization

SSO proves who you are; per-secret annotations and one namespace-level ConfigMap decide what you may see (lib/authz.ts). The app's ServiceAccount executes the K8s calls, so SSO users need no cluster identity.

Decision order​

  1. Admins always pass — KRYPTON_ADMIN_GROUPS / KRYPTON_ADMIN_USERS (matched against SSO groups / lowercased email).
  2. Per-secret annotations override everything below. If a secret has any allowed-groups/allowed-users, only those decide.
  3. Namespace fallback in ConfigMap <app-namespace>/krypton-access, key access.json (cached 60s in memory).
  4. No rules anywhere → visible to all authenticated users (open by default, restricted once rules are added).

Until any admin is configured, every authenticated user is treated as admin (bootstrap mode — set admins promptly).

Per-secret annotations​

# What a Krypton-managed Secret looks like in etcd.
# Per-secret annotations override the namespace fallback in krypton-access.
apiVersion: v1
kind: Secret
metadata:
  name: database-credentials
  namespace: krypton-test
  labels:
    krypton.io/managed-by: krypton
  annotations:
    krypton.io/managed-by: krypton
    krypton.io/version: '3'
    krypton.io/description: Primary database credentials
    krypton.io/allowed-groups: dev-team, database-admins
    krypton.io/allowed-users: alice@company.com
    krypton.io/last-modified-by: alice@company.com
type: Opaque
data:
  DATABASE_URL: cG9zdGdyZXM6Ly9kYjppbmZyYS1vbmx5QGtleXM= # illustrative base64, never plaintext # pragma: allowlist secret
  DB_PASSWORD: czNjcjN0LW9ubHktaW4tZXhj bXBsZXM= # pragma: allowlist secret

Managed in the UI on the secret form:

metadata:
  annotations:
    krypton.io/allowed-groups: 'dev-team, database-admins'
    krypton.io/allowed-users: 'alice@company.com'

Namespace fallback (access.json)​

{
  "frontend-ns": {
    "groups": ["AzureAD-Frontend-Team"],
    "users": []
  },
  "production": {
    "groups": ["dev-team", "database-admins"],
    "users": ["alice@company.com"]
  }
}

Namespaces absent from the map are open to all authenticated users until restricted. An invalid access.json is ignored with a warning (fail-open to step 4, not a crash); a missing ConfigMap simply means no namespace rules.

Creation is special​

A new secret has no annotations yet, so creating in a namespace is decided by the namespace rules alone — the per-secret allowed groups/users you set in the form only take effect after the secret exists. The secrets list response includes canCreate so the UI disables creation upfront when the rules exclude you (POST still enforces server-side: 403).

Managed-only mode​

Default KRYPTON_MANAGED_ONLY=true: secrets without krypton.io/managed-by: krypton are hidden entirely — excluded from lists, 404 on direct access (read, edit, delete, history, restore, restart) — so K8s-level secrets created outside Krypton can't be touched by accident. Set KRYPTON_MANAGED_ONLY=false to show everything again (legacy adopt-on-edit: saving an external secret stamps Krypton annotations onto it).

Optional K8s-native impersonation​

If your API server trusts the same OIDC issuer as the app, set KRYPTON_IMPERSONATION=true and Krypton forwards Impersonate-User/Impersonate-Group headers so the human's RBAC is evaluated instead of the ServiceAccount's. Default is false (hybrid mode above).
