Authorization

SSO proves who you are; per-secret annotations and one namespace-level ConfigMap decide what you may see (lib/authz.ts). The app's ServiceAccount executes the K8s calls, so SSO users need no cluster identity.

Decision order​

After namespace scope and live-object visibility checks:

  1. Admins always pass authorization — K8STON_ADMIN_GROUPS / K8STON_ADMIN_USERS (matched against SSO groups / lowercased email).
  2. Per-secret annotations override everything below. If a secret has any allowed-groups/allowed-users, only those decide.
  3. Team + namespace fallback in ConfigMap <app-namespace>/k8ston-access, key access.json (cached 60s in memory). Namespace members see all secrets; team members see only their team's secrets (see Teams).
  4. Confirmed absence of rules → visible to all authenticated users (open by default, restricted once rules are added). A policy read/validation failure returns 503, not an open-policy decision.

Until any admin is configured, every authenticated user is treated as admin (bootstrap mode — set admins promptly).

Per-secret annotations​

# What a K8ston-managed Secret looks like in etcd.
# Per-secret annotations override the namespace fallback in k8ston-access.
apiVersion: v1
kind: Secret
metadata:
  name: database-credentials
  namespace: k8ston-test
  labels:
    k8ston.io/managed-by: k8ston
  annotations:
    k8ston.io/managed-by: k8ston
    k8ston.io/version: '3'
    k8ston.io/description: Primary database credentials
    k8ston.io/allowed-groups: dev-team, database-admins
    k8ston.io/allowed-users: alice@company.com
    k8ston.io/team: team1
    k8ston.io/last-modified-by: alice@company.com
type: Opaque
data:
  DATABASE_URL: cG9zdGdyZXM6Ly9kYjppbmZyYS1vbmx5QGtleXM= # illustrative base64, never plaintext
  DB_PASSWORD: czNjcjN0LW9ubHktaW4tZXhj bXBsZXM=

Managed in the UI on the secret form:

metadata:
  annotations:
    k8ston.io/allowed-groups: 'dev-team, database-admins'
    k8ston.io/allowed-users: 'alice@company.com'

Annotations use a simple comma-separated list with no quoting or escaping for literal commas. Create/PUT allowedGroups and allowedUsers arrays accept at most 256 entries each, with at most 256 UTF-8 bytes per raw entry, including surrounding whitespace. Each entry is trimmed using the same whitespace rules as the reader. Comma-containing, empty, whitespace-only, or oversized entries return 400 before any Secret/snapshot write, without echoing values or dropping entries. Order, duplicates, internal whitespace, and case are preserved; groups match exactly and user emails match case-insensitively. Session/impersonation groups retain their separate transport contract; these bounds apply to stored ACL collections.

[] explicitly clears just that annotation; omitted PUT fields keep their stored values. Both ACLs empty means namespace fallback, which can intentionally be open. Omitted create fields default to []. The UI's comma-list fields still split on commas, trim, and discard blank segments before submitting: team-a, ,team-b becomes ["team-a", "team-b"], and a blank field submits []. The UI cannot express a literal-comma principal; API ["team-a,team-b"] is rejected rather than split.

ACL input upgrade: previous API versions accepted comma-containing entries that expanded into multiple principals, and whitespace-only entries that could restore open fallback. Update API callers and all writer replicas to this validation contract. Existing annotations are not rewritten or migrated; reads still split/trim/drop blank segments, and omitted PUT fields and restores retain existing ACL values. Review and correct affected live ACLs: CSV cannot recover the original array intent.

Namespace fallback (access.json)​

{
  "frontend-ns": {
    "groups": ["AzureAD-Frontend-Team"],
    "users": []
  },
  "production": {
    "groups": ["dev-team", "database-admins"],
    "users": ["alice@company.com"],
    "teams": [
      { "name": "team1", "groups": ["team1-dev"], "users": [] },
      { "name": "team2", "groups": [], "users": ["bob@company.com"] }
    ]
  }
}

Namespaces absent from a valid map are open to all authenticated users until restricted. {} and namespace entries with empty rule lists are valid open policies. Entries accept groups and users string arrays plus an optional teams array (see Teams); omitted lists default to empty, and unknown fields are rejected to catch misspelled rules. Each policy array has the same 256-entry / 256-UTF-8-byte ceilings; a violation is invalid policy, not an open fallback. Namespace lookups use own properties, so a valid namespace named constructor follows the same absent/empty/explicit rules.

Unlike annotations, namespace JSON arrays preserve each entry exactly, including literal commas and surrounding whitespace; they are not split or trimmed. { "groups": ["team-a,team-b"] } matches only that whole group, not either component. The same applies to users (with existing case-insensitive email comparison). This representation remains available for comma-containing principals when namespace fallback applies; explicit per-secret ACLs still take precedence.

Only a Kubernetes 404 reading the ConfigMap means no namespace rules exist. An existing ConfigMap with missing/empty access.json, invalid JSON/schema, or a failed read (including 403 and timeout) yields 503 { "error": "Namespace access policy is unavailable" } for decisions needing namespace policy. Admins and explicit live-secret ACL decisions keep their precedence and do not require a policy read.

Each process caches valid policy or confirmed absence for 60 seconds from read completion. Concurrent misses share a single read. At expiry, requests wait for a fresh policy; if refresh fails, the old policy is not used. Failures are not cached, so the next request retries. Changes may take up to one cache TTL to be observed by each process. Logs contain only a failure category and, for API read failures, a numeric HTTP status; policy contents and raw transport errors are omitted.

Upgrade: repair malformed ConfigMaps and read permissions before rollout. An intentionally open existing ConfigMap must contain valid access.json: '{}'.

Teams​

Each namespace entry may define up to 64 teams:

{
  "production": {
    "groups": ["platform-leads"],
    "users": [],
    "teams": [{ "name": "team1", "groups": ["team1-dev"], "users": [] }]
  }
}

Secrets opt into a team with the k8ston.io/team annotation (one team per secret; missing/blank means unassigned). Team names are DNS labels (lowercase, 1–63 chars) and must be unique per namespace. Nested groups/users follow the same 256-entry / 256-byte ceilings and exact-match semantics as namespace arrays (groups case-sensitive, users case-insensitive).

  • Namespace members see everything — every team plus unassigned secrets.
  • Team members see only their team's secrets. Unassigned secrets use namespace rules alone, so team membership never grants them.
  • Empty team rules grant nothing (unlike empty namespace rules, which are open): a team with no members is visible only to namespace members — or to everyone when the namespace itself is also unrestricted.
  • Unknown teams fail closed: a secret assigned to a team missing from the policy is denied unless the namespace is completely unrestricted.
  • Per-secret ACLs still win: an explicit allowed-groups/allowed-users annotation decides alone, ignoring both namespace and team rules.

The secrets list shows a team dropdown (filter) and each secret's team; the create/edit form assigns the team. Moving a secret to another team (or to unassigned) requires creation rights in the target, so members cannot escalate secrets into teams they cannot create in. Unknown teams are rejected with 400; forbidden targets with 403.

Teams upgrade: deploy the app before adding teams to access.json — older releases reject the unknown field as invalid policy (503). Existing policies without teams and secrets without the annotation behave exactly as before.

Creation is special​

A new secret has no annotations yet, so creating is decided by the namespace and team rules for the chosen target — the per-secret allowed groups/users you set in the form only take effect after the secret exists. Unassigned creation uses namespace rules alone; assigned creation also accepts the target team's members. The secrets list response includes canCreate (unassigned), teams, and creatableTeams so the UI disables creation upfront when the rules exclude you (POST still enforces server-side: 403). Policy failures return 503 for non-admin creation and list requests. Lists need the policy for canCreate even when empty or containing only explicitly authorized secrets; they return an error rather than a partial list or an invented creation hint. Admin lists degrade to empty team hints instead of failing when only the teams lookup is unavailable.

Managed-only mode​

Default K8STON_MANAGED_ONLY=true: secrets without k8ston.io/managed-by: k8ston are hidden entirely — excluded from lists, 404 on direct access (read, edit, delete, history, restore, restart) — so K8s-level secrets created outside K8ston can't be touched by accident. Set K8STON_MANAGED_ONLY=false to show unmanaged live secrets (legacy adopt-on-edit: saving an external secret stamps K8ston annotations onto it).

History uses current live authorization​

History objects (k8ston.io/kind=history) are always excluded from lists and return 404 on direct GET/PUT/DELETE/history/restore/restart routes, in both managed-only modes and for admins too. A managed annotation cannot override the history label. All named-secret operations share lib/secret-access.ts, which loads a current live object, checks visibility, then evaluates its authorization.

Read history via /secrets/:liveName/versions and restore via /secrets/:liveName/restore. These endpoints check the live object's current ACL before accessing snapshots. Copied historical ACLs never grant access: a user denied by the current live rules cannot regain access through an older snapshot that listed them. Clients previously addressing snapshot names must switch to the live endpoints.

Optional K8s-native impersonation​

Set K8STON_IMPERSONATION=true when the session email and groups match the intended Kubernetes RBAC subjects. The app's ServiceAccount must have the impersonate verb for those users and all their groups; their RBAC then authorizes the human operations. K8ston's visibility and application ACL checks still apply, including to users considered K8ston admins.

  • Namespace requests, live-secret CRUD, history reads/writes/pruning, and all Deployment/StatefulSet/DaemonSet lists and patches carry the human identity.
  • The session email is sent as Impersonate-User. Every session group is a separate repeated Impersonate-Group header, including when a group contains a literal comma. There is no application group-count cap, joining, or splitting.
  • Values must be nonempty printable ASCII with no leading/trailing whitespace. Unsupported user/group values fail with 400 rather than being silently changed. API-server/proxy header-size limits can reject the whole request; groups are never silently truncated. Impersonated API requests do not follow redirects.
  • The SDK's supported per-request httpApi extension sends raw header pairs, preserving its ServiceAccount authentication and TLS dispatcher and the JSON-Patch content type. Clients and KubeConfig hold no human identity.
  • The application's access-policy ConfigMap is deliberately fetched as the ServiceAccount, with the same process-wide 60s cache and coalesced reads above. Its cache never depends on the requesting human's Kubernetes permissions.
  • Default K8STON_IMPERSONATION=false uses hybrid mode. Explicit AUTH_DISABLED=true bypasses human impersonation for local development. A real signed session for dev@k8ston.local is impersonated just like any other user.

Upgrade: earlier versions overwrote repeated groups, processed only the first 32 groups, and omitted impersonation on workload lists. Review ServiceAccount impersonation grants for the full group set and human workload list/patch RBAC. Map unsupported identity values to header-safe IdP subjects and matching RBAC bindings; failure to represent an identity never falls back to the service identity for secret or workload operations.
