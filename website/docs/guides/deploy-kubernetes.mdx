# Deploy to Kubernetes

Manifests live in `app/k8s/`. Two topologies: namespace-scoped (default, least
privilege) or cluster-wide (centralized multi-namespace dashboard).

## Namespace scope (default)

Before applying the examples, configure your OIDC client/public URL and admins,
add namespace rules for the actual targets, and replace the Deployment's `latest`
image with a published tag. The example access ConfigMap omits `k8ston`, so its
fallback access is open until you add a rule. Keep `AUTH_DISABLED=false` in production.

For reusable images, prefer runtime `APP_URL` without a conflicting build-time
`NEXT_PUBLIC_APP_URL`. Provision a private env file outside the checkout (permissions
`0600`) with your `OIDC_CLIENT_SECRET` and a fresh `SESSION_SECRET` from
`openssl rand -hex 32`; never put actual credentials in Git or shell history.
From the repository root:

```bash
kubectl apply -f app/k8s/namespace.yaml -f app/k8s/serviceaccount.yaml -f app/k8s/role.yaml
kubectl apply -f app/k8s/configmap-access.yaml -f app/k8s/configmap-app.yaml
kubectl -n k8ston create secret generic k8ston-oidc \
  --from-env-file=/secure/path/k8ston-oidc.env
kubectl apply -f app/k8s/deployment.yaml
kubectl -n k8ston rollout status deployment/k8ston
```

Do not apply the entire directory indiscriminately: it includes broader cluster
RBAC and an OIDC Secret template with placeholder values.

What you get:

| Manifest                | Purpose                                                         |
| ----------------------- | --------------------------------------------------------------- |
| `namespace.yaml`        | `k8ston` namespace                                              |
| `serviceaccount.yaml`   | `k8ston` ServiceAccount (the identity that calls the K8s API)   |
| `role.yaml`             | `secrets` full verbs + `configmaps` read, own namespace only    |
| `configmap-app.yaml`    | Non-secret app config (`K8STON_*`, `OIDC_*`, `NEXT_PUBLIC_*`)   |
| `configmap-access.yaml` | Namespace fallback rules (`access.json`)                        |
| `secret-oidc.yaml`      | Template for `k8ston-oidc` (create with real values instead)    |
| `deployment.yaml`       | App deployment (non-root `65532`, read-only root FS, port 3000) |

Then expose via Ingress/Route with TLS and register the OIDC redirect URI
(`https://<host>/api/auth/callback`).

Liveness and readiness probes hit `/api/config` — unauthenticated and free of
K8s/OIDC calls, so it is safe to probe (the Helm chart probes the same endpoint).
They do not verify authentication or Kubernetes connectivity; test real sign-in,
allowed Secret operations, and an unauthorized-user denial separately.

## Cluster scope (multi-namespace dashboard)

Set `K8STON_SCOPE=cluster` in `configmap-app.yaml`, apply `clusterrole.yaml`
(instead of, or in addition to, `role.yaml`), and optionally narrow with
`K8STON_NAMESPACES="team-a,team-b"`:

```bash
kubectl apply -f app/k8s/clusterrole.yaml
```

The ClusterRole adds `namespaces` (get, list, watch) on top of the namespace
permissions. A configured `K8STON_NAMESPACES` allowlist resolves/checks locally
without namespace-list calls, so curated deployments can instead grant resource
permissions in just those namespaces. Without an allowlist, failed/incomplete
namespace discovery returns an error; it no longer falls back to the pod namespace.
An application allowlist does not narrow the ClusterRole's Kubernetes permissions.
For curated namespaces without a ClusterRole, use matching namespaced Roles or
the Helm chart's `rbac.extraNamespaces` option.

## Enabling "Restart apps"

The feature is disabled by default (least privilege). To enable it, do **both**:

1. Set `K8STON_RESTART_ENABLED: 'true'` in `configmap-app.yaml`.
2. Uncomment the `apps` rule (deployments/statefulsets/daemonsets: get, list,
   watch, patch) in `role.yaml` (or `clusterrole.yaml`).

Without the flag, the UI button + hint are hidden and the API returns 403.
Without the RBAC rule, the API fails closed at the Kubernetes API.

## Container image

The `Dockerfile` (repo root, pnpm workspace context) builds
`ghcr.io/egose/k8ston:<tag>` — published on `v*.*.*` tags by the
_Publish Docker image_ workflow:

```bash
docker build -t k8ston:sandbox -f Dockerfile .
```

The image runs the Next.js standalone server (`node app/server.js`) as UID
`65532` on port 3000, matching `app/k8s/deployment.yaml`. K8ston is stateless
(no separate application database). Replicas share Kubernetes state and must use
the same signing key, annotation prefix, and retention configuration. Environment
changes require a rollout; replacing the signing key invalidates existing sessions.

## Prefer Helm?

The [Helm guide](/guides/deploy-helm/) covers the `helm/main` chart
(`helm/k8ston` subchart, NetworkPolicy, OpenShift Routes). Prefer raw manifests
when you want minimal moving parts; prefer Helm when you want templated RBAC
scope, restart wiring, and access config in one values file.
